# 设计决定与未完成项

## 阶段一：写入授权边界（Private 模式仍未满足验收）

### 实际阻塞

Private 模式中当前客户端脚本与 Coding Agent 在同一操作系统用户下运行。脚本需要读取 `approval.key` 才能生成请求 HMAC，因此同一用户权限下的 Agent 也能读取该密钥、绕开交互提示并自行签名。TTY 检查、短时签名及一次性 nonce 只能限制脚本误用、签名篡改和重放，不能证明操作者是用户，也不能构成逐次用户授权。

### 当前处理

Private 模式保留短时、绑定 HTTP 方法/路径/正文的 HMAC 与一次性 nonce，作为请求完整性和重放防护；**不把它视作用户授权**。阶段一 Private 写入授权边界未完成，不得用于要求 Agent 无法自主写入的部署。

Secure 模式新增独立 Ed25519 审批流程和读写凭据隔离，详情见阶段四。Secure 方案的信任边界依赖 Agent/审批者 OS 账户、终端及 Docker daemon 权限确实隔离；若 Agent 和审批者同 UID 或 Agent 可访问审批私钥、写 token、审批终端或 Docker daemon，隔离失效。

### 可行部署方案

1. **Secure 独立审批 CLI**：Agent 只持有只读 token 并准备写入请求文件；运行在独立 OS 账户的审批者使用专用私钥和写 token，在交互终端检查实际请求正文、明确批准后直接提交。服务只持有公钥并消费绑定 HTTP 方法/路径/正文的一次性签名。
2. **独立审批服务**：用户登录的浏览器/可信设备展示完整内容并记录确认，审批服务使用 Agent 不可读取的凭据签发一次性授权。当前没有外部审批身份服务，不宣称已实现该模式。

独立 OS 用户/终端及权限部署必须实际配置并验收，应用不能从同 UID 环境中自行创造可信身份隔离。若 Agent 能够调用审批工具并控制审批终端，或读到私钥/写 token，则不能视为独立审批。

## 项目解析及检索副作用

`mem-search` 不应调用具有创建/绑定副作用的 `POST /projects/resolve`。已改为调用只读项目查找接口：未解析项目时返回错误，提示先通过用户触发的项目/保存流程创建或绑定；不会因首次自动检索在服务端创建项目或仓库映射。Git remote 对新项目的自动建档仍可由显式项目初始化/`mem-save` 流程触发，遵循 PRD 的 remote 识别规则。

## 阶段二：项目合并冲突规则

项目合并按稳定 ID 将源项目的所有项目知识库及记忆移动到目标项目，不做内容相似度或语义冲突判断。源项目默认库转为普通项目库并标记“（合并）”，确保目标已有默认库不发生冲突、源记忆不丢失。两个项目绑定同一规范仓库时保留目标绑定，源的重复映射随源项目删除；不同仓库映射迁移至目标。合并以单个 SQLite 事务执行，并记一条项目操作记录。该简单规则以保留数据、确定性处理唯一仓库映射冲突为目标；语义冲突识别不属于本阶段。

删除项目及非默认知识库前要求明确确认；此操作永久删除其所含记忆，服务端同步清理对应修改历史。永久删除记忆也要求先软删除并明确确认。

## 阶段二：验证边界

阶段二的 Go API/SQLite 行为测试、静态检查、构建及 Shell 语法检查已在 Go 1.24 Alpine 容器运行；本机 Pi/Codex 的 mem-save/mem-search Skill 已完成项目/共享范围检索、Secure 提案、自动化 CLI 审批及回查，但其他管理 Skill 和真人用户验收仍未完成。Private 模式逐次授权仍未解决；管理写接口沿用其 HMAC 完整性/防重放机制，不因此宣称具备用户身份验证或严格逐次授权。Secure 模式新增边界不改变 Private 模式既有缺口。

## 阶段三：接入与管理界面的实现边界

### MCP 写工具

MCP 通过 `/mcp` 提供无会话的 Streamable HTTP JSON-RPC；读取工具直接复用现有 API handler。写工具要求参数携带现有 REST 请求格式的 `write_signature`，由适配器交给同一写入 handler 校验一次性签名，不绕过 API 的防重放校验。Private 模式签名不是用户授权。Pi 1.6.0 和 Codex CLI 0.171.0 已实际调用读取及带测试 HMAC 的写入工具成功；Pi 缺少签名时被输入 Schema 拒绝，Codex headless 默认 `approval=never` 时拒绝 MCP 调用，使用 `--approve-for-me` 后通过。此前测试签名由测试端预先生成，验证协议/传输/服务端校验，不代表正常客户端具有用户确认。

Secure 模式 Agent 的只读 token 可调用 MCP 写工具准备请求 envelope，但不会直接修改数据；独立审批 CLI 读取 envelope 后以 ACL 授权的写 token 和 Ed25519 审批签名向 REST API 提交。MCP 不持有审批私钥。

### Web 写操作

Private 模式 Web Console 改用管理员会话写入，不依赖浏览器 `crypto.subtle` 或 HMAC 密钥输入。首次部署通过 `MEMDOCK_ADMIN_PASSWORD` 初始化单管理员密码，持久化 PBKDF2 哈希；会话使用随机 HttpOnly、SameSite=Strict Cookie、12 小时有效期及 CSRF token，修改密码会使全部旧会话失效。Private API/MCP 的 HMAC/静态密钥客户端契约不变；Console 登录不是 Private API/MCP 的认证，也不建立 Agent 与操作者之间的 OS 身份隔离。

普通 HTTP 不加密密码、会话或数据，建议使用 HTTPS 或可信加密网络；不可在不可信网络传输。Secure Web 不持有写 token/审批私钥；用户确认后只导出 REST 请求 envelope，须由独立审批 CLI 交互提交。Secure 独立审批边界不受 Private 管理员会话影响。

### 来源字段

当前记忆模型没有记录来源 Agent 字段。阶段三 Web/MCP 显示知识库名称、类型作为检索/列表来源；不得将其误认为来源 Agent。若产品仍要求来源 Agent，需另行明确写入契约及历史数据处理后再扩展 Schema。

### 复审修正

- 记忆列表将标签聚合放在同一 SQL 查询，不在遍历 `rows` 时再次占用数据库连接；以 `SetMaxOpenConns(1)` 的 HTTP 测试覆盖带标签结果。
- 项目默认库不能变为共享库或迁移到其他项目，避免源项目失去默认库；常规项目库可转共享或迁移，更新显式计算 `is_default`，不依赖更新语句中的旧 `kind` 判断。
- 记忆列表必须提供 `project_id`；指定知识库须属于该项目或为共享库。按 ID 的详情、历史和修改/删除操作也必须携带项目范围，跨项目访问返回 404。该范围检查防止 API 调用误触其他项目数据，不等同于用户身份认证。

## 阶段四：部署、安全与交付

### 恢复边界

SQLite 恢复要求先停止 MemDock 服务。恢复前将来源数据库验证为受支持的 MemDock schema（不仅检查 `user_version`，还核实完整性、版本对应的表/列）；使用同一个 SQLite 连接对来源执行 `VACUUM INTO` 生成已验证的暂存快照，以纳入来源可能存在的 WAL 提交。替换时把旧主库、`-wal`、`-shm` 移入同目录临时保留文件，再原子安装暂存数据库；安装失败时反向恢复所有旧文件。安装成功后清理旧副本；若清理失败，会报告错误并保留副本路径，不能把副本误认为当前数据库。

验证失败发生在改动目标文件之前。回归测试通过异常终止子进程制造有效残留 WAL/SHM，验证失败恢复保留原始主库和 sidecar，成功恢复不重放旧 WAL、恢复后的 integrity/schema/data 检查通过。停服和不并发写是必要前提；文件系统/宿主机在多文件移动过程中突然断电或被强制终止的恢复演练仍需在真实部署环境进行。

### 身份与代理信任边界

Secure 模式要求读 token、写 token、Ed25519 公钥及 `MEMDOCK_PROJECT_ACL_FILE`。ACL 以 token 的 SHA-256 摘要映射 `read`、`write`、`admin` 角色和项目 ID；共享库读写使用独立标志，项目创建、状态中的全局数量和整库备份仅 admin。未配置 ACL 或未授权项目默认拒绝。read token 必须为 read-only；write token 仅能访问 ACL 授权的项目，写操作仍需一次性 Ed25519 审批。ACL 文件修改后需重启服务。Private 模式仍无应用身份 ACL，依赖受信网络。

Agent 仅使用项目范围内只读 token；Web、Secure 写入 Skill 与 MCP 写工具准备请求文件，不直接改变数据。独立审批者通过可信渠道接收文件，在自己的终端运行 `memdock-server approve-request REQUEST.json`，检查准确请求正文并明确输入 `approve`，再由 CLI 签名和发送。服务器不存私钥。独立 OS 账户、TTY、私钥 `0600` 权限和 Docker daemon 权限必须真实分离；Agent 若拥有审批者 UID、私钥、写 token、可控制审批终端或 Docker daemon，即能绕过该边界，部署不可宣称严格逐次授权。

TLS 代理模式除校验 `X-Forwarded-Proto: https`，还校验 TCP 连接源地址落在配置的 `MEMDOCK_TRUST_PROXY_CIDRS`。客户端直接连接即使伪造转发头也会拒绝。可信代理必须覆盖客户端提供的转发头并限制后端网络访问；CIDR 配置过宽、同网段恶意主机或代理保留客户端伪造值仍会破坏信任。直接 TLS 模式不信任转发头，要求真实 TLS 连接。真实代理网络和部署拓扑仍须验收。

### 入口接入边界

Secure Web（浏览器 Basic）、REST、MCP 与管理 Skill 的每个项目/知识库请求均检查 bearer/basic token 对应 ACL；项目与知识库列表按权限过滤，默认检索不返回无权访问的共享库，整库备份只允许 admin。跨 token 项目越权、共享范围、MCP 请求授权、备份拒绝及签名写入由自动化回归覆盖。

Secure Web 写操作导出审批 envelope；mem-save/update/delete/kb-create/project-rename Skill 和 MCP `memory_save/update/delete` 在 Agent 只读 token 下生成结构化请求，不直接写入。Secure `mem-save` 在用户明确触发后生成 `0600` 请求；有 TTY 时额外要求 `y`，无 TTY 时只准备待审批请求。独立审批 CLI `approve-request` 校验 envelope、在 TTY 展示正文并要求输入 `approve` 后签名提交。MCP 提案 → `script` 伪终端审批 → Secure TLS REST 写入 → SQLite 持久化已通过本地端到端测试；本轮 Pi/Codex Skill 的项目库/共享库提案也经 CLI 写入和 Skill 检索回查通过。所有终端确认均由自动化输入，不是真人确认；请求文件仍须经可信渠道转交，文件生成不等于已审批。

## 阶段五：整体验收及性能结果（开发方记录，未作用户验收）

- 在 Linux x86_64、2 vCPU、约 7.5 GiB RAM 的 Docker 29.1.3 环境，以 Go 1.24 Alpine 容器运行 opt-in 100,000 条 SQLite 测试；单并发先预热 10 次，另测 100 次，数据库 FTS 搜索 P95 12.363 ms、本地 HTTP API 搜索（计时读完整响应体）P95 13.440 ms、API 保存（计时读完整响应体）P95 9.420 ms。低于 PRD 建议的 50 ms / 100 ms；该结果仅代表合成数据、本机单并发，不构成生产承诺。复现实验命令和口径见 [阶段五任务记录](tasks/05-整体验收.md)。
- 已通过 Docker 镜像运行 Private 服务，实际 HTTP 创建项目/保存/查询，并下载备份、停服恢复、重启后再次查询。Go 测试、vet、build、Shell 语法及 diff 检查通过。
- 本轮本机补验：Playwright/Chromium 下载 Secure Web 审批文件，经 `approve-request` 伪终端自动输入确认后写入 TLS 服务并读回；真实 Pi 1.6.0/openai-codex 与 Codex CLI 0.171.0 交互 TUI 均成功 MCP 搜索。Codex 在明确用户请求下触发 `memory_save`，pexpect 自动确认 TUI 一次性 MCP tool permission 后返回 `approval_required=true` proposal，数据库未保存（不是人工审批）。Codex 非交互 `exec` 的默认 approval policy 为 `never`，错误为 `MCP tool call requires approval, but approval policy is never`；交互模式 `--ask-for-approval on-request` 可运行。临时自签 CA-as-leaf TLS 配置未完成握手；临时 CA 签发且含 SAN/serverAuth 的 leaf、系统 CA+临时 CA trust bundle 可正常工作。代理验证 Codex `initialize`、`notifications/initialized`、`tools/list`、`tools/call` 与协议版本 `2025-03-26`；首个 initialize 不带版本头，符合流程。服务/脱敏代理日志及 CLI/会话可读输出未发现凭据值；递归检查 Codex 临时状态目录另发现初始诊断进程将三个本次生成的测试 token 写入 `/tmp` 下 shell snapshot（因完整服务环境被继承），均非用户凭据，已在完成记录后删除临时测试目录；后续交互 Codex 仅接收 read token。
- 尝试不同 UID：`nobody` 可读取获授权项目，直接写入返回 403，且无法读取 0600 私钥；但实际 Pi、浏览器和审批 CLI 均在 ubuntu UID 1000，不能据此声称 Agent/审批者隔离。`/home/ubuntu` 为 0750，Codex/Pi/OAuth 文件仅对该账户可达；未降低权限、复制 OAuth 凭据或创建永久账户。ubuntu 具 sudo/docker 权限。
- 仍未完成实际模型 Agent 与审批者 OS/终端/Docker daemon 分离、Codex MCP 审批提案与 CLI 的端到端交接（MCP 本轮只验证提案产生且未保存）、Tailscale 第二设备/项目绑定、生产代理与日志审计、跨 OS 文件交接、Compose/ARM64 和生产恢复演练。Skill 提案到 CLI 的本机链路已通过，但 CLI 确认由自动化输入且同 UID，不证明真实审批者隔离。Tailscale 仅确认当前 VM 在线。不得标记阶段验收完成；由用户决定最终验收。

`POST /api/v1/projects/resolve` 会创建项目或绑定仓库，现已和其他写端点一样强制 HMAC（Private）或 Ed25519（Secure）一次性签名；无副作用的 `/projects/lookup` 供自动查询使用。
