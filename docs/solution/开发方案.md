# MemDock V1.0 开发方案

## 1. 目标与范围

本方案以 [PRD](../prd/PRD.md) 为基线，先实现项目识别、主动保存和按需检索的可用闭环，再逐步完成管理、接入和部署能力。V1.0 不引入向量检索、外部 AI 服务、自动总结或 Agent 自主写入。

用户新增的多知识库需求以本方案为准：默认搜索包含当前项目库与共享库，PRD 中仅搜索当前项目的原描述尚待同步。

服务采用 Go 单体和 SQLite，REST API、MCP 与 Web 共用业务逻辑；Skill 是优先接入方式。性能指标以实测结果为准。

## 2. 总体实现

- **客户端**：轻量脚本识别 Git 仓库并调用 HTTP API；搜索 Skill 可按任务自动使用，写入 Skill 仅响应用户明确要求。
- **服务端**：Go HTTP 服务负责项目映射、记忆管理、搜索、认证授权和管理接口；MCP 复用同一业务服务。
- **存储**：SQLite 保存项目、仓库映射、知识库、记忆、标签及必要的修改历史；FTS5 建立搜索索引。
- **管理与部署**：Web 静态资源由同一服务提供，Docker 单容器运行，数据库目录持久化。

初期按职责划分代码目录即可，以实际需要确定接口，不预先搭建通用框架。API 字段、错误格式和迁移细节在对应阶段实现前确定并记录。

## 3. 核心设计

### 3.1 项目识别

客户端在当前目录及 Git 子目录、worktree 中获取仓库信息，优先使用明确绑定，其次查找已有 remote 映射，再使用 origin 创建项目；多个 remote 指向不同项目时要求用户选择。服务端为项目生成稳定 ID，一个项目可绑定多个仓库，仓库名称相同不自动合并。

统一处理 SSH、HTTPS 和 SSH URL，去除认证信息、末尾斜杠及 `.git` 后缀，主机名统一大小写，并保留识别所需的非默认端口；仓库路径大小写遵循实际托管平台规则。客户端不得上传 URL 中的凭证。

无 Git 仓库或 remote 时，默认使用当前文件夹名作为项目名称，用户可修改名称，选择已有项目或创建新项目，并将当前目录绑定到该项目的稳定 ID。不仅凭名称自动合并；同名时由用户选择。其他设备需要使用同一项目时，用户在该设备选择并绑定，后续也可绑定 Git 仓库。

### 3.2 记忆管理

支持多个知识库，每个库具有稳定 ID、名称和类型：项目库绑定一个项目，共享库供所有项目查询。每个项目设有默认项目库；用户可创建其他项目库或共享库，并明确指定类型和归属。

记忆包含所属知识库、标题、正文、分类、标签、来源、状态及创建和更新时间，可选保存会话标识，不保存完整聊天。默认保存到当前项目的默认项目库；用户可明确指定共享库或其他项目库，目标有歧义时先选择。创建、更新和删除均需用户明确触发，包括共享库的写入；更新保留必要历史，删除采用软删除，支持恢复和永久删除。默认搜索只返回有效记忆。更新目标不明确时先让用户选择。

标签用于分类筛选，Agent 可根据内容建议标签，用户可指定或修改；标签不决定知识库类型或访问范围。改变知识库类型或项目归属须由用户明确操作。

历史记忆是供参考的数据，不能覆盖当前用户要求或更高优先级指令；Agent 使用前应结合当前代码判断是否仍有效。

### 3.3 搜索

默认查询当前项目的所有项目库和所有共享库，不查询其他项目库；用户可明确指定知识库，访问其他项目库须明确指定。结果标明所属库及类型，按有效状态过滤，默认返回最多 5 条并限制内容长度；支持分类、标签和排序。使用 FTS5 trigram 搜索较长关键词，针对短于三个字符的中文词及技术缩写提供普通匹配回退，覆盖中英文混合和多关键词。具体匹配和排序规则通过测试样例确定，不承诺语义理解。记忆变更、软删除和恢复时保持索引一致。共享经验使用前应结合当前项目判断适用性，冲突时遵循当前用户要求及项目实际约定。

### 3.4 安全边界

- Private 模式默认面向受限 Tailnet，服务不直接暴露公网；Secure 模式要求认证、授权和可信 HTTPS 接入，配置缺失时拒绝启动。
- 自动检索与写入分离权限。Skill 文字约束不能作为安全边界；需要严格限制写入时，通过独立授权凭据或本地命令适配器完成明确授权。Private 模式默认无应用认证时，网络内访问者不具备由服务强制区分的读写权限，不能声称已实现严格隔离；启用隔离时须配置实际授权机制。
- Web 管理和 API 校验相应权限；日志不记录凭据或完整记忆正文。反向代理终止 TLS 时限制后端只能由可信网络访问。

实现前先明确用户触发写入的实际操作和授权流程，选择满足验收的最简单机制，不并行建设多套授权方案。仅区分读写凭据不能证明每一次写入都由用户明确授权；如果 Agent 可自行使用写入凭据，还需验证授权边界。

## 4. 分阶段实施

### 阶段一：核心链路

1. 初始化 Go 服务、配置、健康检查、SQLite 连接和版本化迁移；启用外键，根据实际并发和部署环境确定 WAL 与忙等待配置。
2. 实现项目识别与仓库映射、项目库和共享库的创建及指定保存、跨库搜索 API，以及基本输入校验和错误响应。
3. 先实现常见 origin 的 SSH/HTTPS 地址规范化与客户端识别，验证项目隔离；随后在本阶段补齐无 Git 或 remote 时按名称选择或创建并绑定项目、worktree 和多 remote 歧义处理。不得因名称相同而自动合并项目。
4. 实现 `mem-save` 与 `mem-search`，打通真实客户端的保存与检索。
5. 验证默认和指定库搜索、共享库跨项目可见、其他项目库默认隔离、中文搜索、重启后持久化和用户触发写入流程。

阶段产出：可在本地运行并完成一次真实保存和检索的服务与 Skill。此阶段不代表完整安全模式或 V1.0 已完成。

### 阶段二：记忆与项目管理

补齐记忆列表、详情、更新、软删除、恢复、永久删除和修改历史；实现知识库及标签管理、项目详情、编辑、仓库绑定和解绑。项目合并前明确实际冲突及处理规则，以调整项目归属为主，不预先实现记忆内容的语义冲突检测或复杂合并流程；保留必要操作记录，删除项目需确认。补齐 `mem-list`、`mem-update`、`mem-delete`，检查索引与数据一致性。

### 阶段三：接入与管理界面

实现共用业务逻辑的 Streamable HTTP MCP，提供 PRD 所列工具，并验证 Codex、Pi 的实际接入能力及权限行为。实现 Web 首页、项目、知识库及记忆管理、搜索和系统状态；支持选择库、管理标签和显示来源，PC 优先并兼容移动端。客户端触发方式以实际版本验证为准。

### 阶段四：部署、安全与交付

完成 Docker 多阶段构建、非 root 运行、Compose、健康检查子命令和 AMD64/ARM64 构建验证；完成 Private / Secure 模式、认证授权、HTTPS 接入和启动配置校验。采用简单可用的方式完成 SQLite 一致性备份、下载、恢复前验证和恢复结果检查，不预先建设复杂备份管理系统；验证容器重建后数据保留。补齐配置说明、Tailscale 和反向代理部署文档。

### 阶段五：验收与性能测试

按 PRD 验证项目识别、记忆管理、自动检索、容器部署和安全要求。准备 10 万条记忆的数据集，在记录的硬件和并发条件下分别测量数据库搜索与完整 API 的 P95；保存 P95 同样实测。50 ms / 100 ms 为建议目标，不作为未经测量的承诺。验证备份恢复、权限拒绝和日志脱敏，并记录未覆盖环境。

## 5. 验证重点

- 仓库 SSH/HTTPS 归一化、凭证剔除、不同仓库隔离、迁移绑定和多 remote 歧义。
- 无 Git 或 remote 时默认使用当前文件夹名、允许修改名称并创建或选择项目，以及同名项目区分、跨设备绑定和后续绑定仓库。
- 项目库和共享库创建、默认及指定保存与搜索、来源展示、标签管理和其他项目库默认隔离。
- 新建、更新、删除、恢复后的搜索结果及修改历史；中文两字词、英文缩写和混合查询。
- 用户明确触发写入、只读凭据拒绝写操作、Secure 模式缺少必要配置时拒绝启动。
- Codex 与 Pi 的实际 Skill/MCP 行为；Docker 重建、备份恢复及数据完整性。
- Web 界面和移动端布局以实际运行验证，性能和多架构支持以测试结果为准。

## 6. 实施约定

各阶段先确定具体接口与验收样例，再按需实现；阶段完成后记录实际验证结果和未验证项。PRD 中的 API 示例和目录结构作为设计参考，新增管理、恢复及备份接口时保持一致的版本和权限规则。

搜索的匹配、排序和短词回退以实际验收样例驱动；性能优化以实测为依据，不预先增加缓存或复杂调优。Web 首页和系统状态保持基本可用，不扩展为监控平台。基础 Docker 持久化可在核心链路阶段提前验证，完整部署和安全交付仍在阶段四完成。
