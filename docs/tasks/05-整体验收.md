## 开发方验证记录

- 环境：Linux x86_64 虚拟机（内核 6.8.0-151-generic），Docker 29.1.3 legacy builder；分配 2 vCPU、约 7.5 GiB RAM。Go 1.24 Alpine 容器执行测试。容器镜像成功构建并以 UID 10001 运行。当前无 Go 本机安装、Docker Compose 插件或 ARM64 设备；Tailscale 已连接但仅确认当前 VM 在线。
- 自动回归：`go test ./...`、`go vet ./...`、`go build ./cmd/server`、`sh -n scripts/*.sh` 均通过；`git diff --check` 通过。测试覆盖项目/知识库隔离、跨 token 越权拒绝、分享库读写授权、Secure REST 直接写入拒绝、MCP proposal、Ed25519 一次性审批、代理源校验、备份 schema 校验及 WAL/SHM 恢复回滚。
- 容器端到端：构建本地镜像并挂载临时命名卷，启动 Private 服务；通过 HTTP 签名创建项目及记忆，搜索命中；下载服务端一致性备份，停服恢复至同一卷，再启动并确认数据可查。此测试验证 API 与恢复链路，不证明用户身份授权或生产环境备份演练。
- Secure 本地端到端：Playwright 1.62/Chromium headless 以 Basic read token 打开 Web、确认生成请求并下载 JSON；该下载文件交由 `approve-request` 在 `script` 伪终端显示，自动输入 `approve` 后用 write token/Ed25519 key 写入 TLS 服务，REST 查询确认数据保存。Pi 1.6.0/openai-codex 与 Codex CLI 0.171.0 交互 TUI 都实际调用 MCP 搜索并返回数据库中的 marker。Codex 在明确用户提示下触发 `memory_save`，一次性允许 MCP tool 后，工具返回 `approval_required=true` / `/api/v1/memories` envelope；SQLite 核对该标题不存在。TUI 的一次性 `Allow` 由 pexpect 自动输入，不是人工操作；Codex 非交互 `exec` 的 client approval policy 默认 `never`，会在请求到达服务端前拒绝；交互 TUI 设 `--ask-for-approval on-request` 后通过。
- Secure Skill 本机端到端：Pi 1.6.0 通过 `--skill` 加载仓库 Skill；Codex CLI 0.171.0 从临时 `CODEX_HOME/skills` 符号链接加载；既有认证文件仅通过临时符号链接复用，未复制凭据或修改全局配置。两客户端只得到 read token，Codex sandbox 仅临时开放 `localhost` 网络。默认和指定范围检索通过；Pi/Codex 默认项目及 Pi 指定共享库保存均先生成 mode 0600 proposal，批准前查询为空，独立 CLI 自动输入 `approve` 写入后再由 Skill 搜索读回，标签经详情 API 核验。测试发现原 Secure `mem-save` 在 Agent 无 TTY 时直接拒绝；现改为 Secure 无 TTY 只生成 proposal，Private 无 TTY 仍拒绝。所有确认均为自动化输入，不代表真人操作。
- Codex transport 复核：第一次临时 TLS 测试用自签 CA 证书直接作为 server leaf，Codex RMCP 记录 `error sending request for url (https://localhost:.../mcp)`，代理未见 HTTP 请求。更换 CA 签发、含 SAN 和 `serverAuth` 的 leaf，并通过 `SSL_CERT_FILE` 提供系统 CA + 临时测试 CA 后，Codex 实际发出 `initialize`（首个请求不带 `MCP-Protocol-Version`）、随后带 `2025-03-26` 的 `notifications/initialized`、`tools/list` 和 `tools/call`；服务分别返回 200/202，工具响应 200。人工对照 `initialize` 响应协议版本 `2025-03-26`、`tools/list` 的 6 项工具。失败日志只记录泛化 TLS 请求错误，没有更细的证书验证子错误；当前通过的是正确签发的临时 CA/leaf，而非生产证书部署。
- 身份/日志部分验证：nobody UID 65534 可读授权项目、直接写被拒且读不到 owner `0600` 审批私钥（父目录可遍历）；服务/脱敏代理日志及 CLI/会话可读输出不含 bearer/signature 值。全量扫描 Codex 临时 CODEX_HOME 时发现，最初一次诊断 `exec` 继承了完整测试服务环境，Codex 在 `/tmp` 的 `shell_snapshots` 环境快照保存了三个本次生成的测试 token；它们不是用户凭据，发现后保留在临时目录直至最终清理。之后的交互客户端仅继承 read token。该 nobody 仅执行 HTTP probe；实际 Pi、Playwright、CLI 均由 ubuntu UID 1000 运行。系统仅有这个可交互普通用户，Codex/Pi 程序及 OAuth 文件位于 mode 0750 的 `/home/ubuntu` 下；为避免改 home 权限、复制 OAuth secret 或创建永久用户，没有让实际模型客户端以 nobody 运行。ubuntu 具 sudo/docker 权限，故不能宣称隔离成立。
- 10 万条性能实验：`go test -tags stage5benchmark ./cmd/server -run '^TestStage5Benchmark100k$' -count=1 -v`。该 opt-in 测试在临时 SQLite 数据库直接生成 100,000 条合成记忆（每 100 条中 1 条包含查询词）；单并发先执行 10 次不计时预热，再分别测量 100 次搜索和 100 次保存。DB 指标计时等价 FTS 查询并遍历/检查 5 条结果；API 指标经过本地 `httptest.Server` 的 HTTP 路由、中间件（Private 模式不要求认证）及 SQLite，计时包括完整响应体读取，搜索校验 5 条结果。保存校验 HTTP 201，预热和测量共增加 110 条。最新复测 P95：数据库搜索 **12.363 ms**，HTTP API 搜索 **13.440 ms**，API 保存 **9.420 ms**。建议值：搜索 <50 ms、保存 <100 ms；本次均达标。末尾核对总数 100,110。合成数据、单并发和虚拟机结果不能外推为生产容量承诺。
- 未覆盖/阻塞：Codex 非交互 MCP 调用受默认 approval policy 阻止（交互 TUI 已验证）；实际模型 Agent 与审批者 OS 身份/终端/Docker daemon 隔离；第二设备 Tailscale、生产 TLS 代理与生产日志审计；跨 OS 审批文件交接、跨设备绑定、Compose 插件、ARM64 image/device、生产备份恢复演练仍未完成。Pi、Codex 与本机 headless browser 的成功记录是 Linux VM 内的本地流程，不代表真实跨设备部署。Private HMAC 和脚本确认不构成严格用户授权。Secure 项目 ACL 与审批请求文件链路已实现并有本地回归测试；生产身份隔离和跨设备部署仍待验收。详情见[待确认问题](../待确认问题.md)。本任务不替用户作 V1.0 验收结论。
