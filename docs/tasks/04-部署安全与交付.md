## 开发

- [X] 支持直接 TLS；代理 TLS 同时校验代理源 IP CIDR 和 `X-Forwarded-Proto`。代理头本身不是信任凭据，后端网络必须限制为可信代理。

## 开发方验证记录

- Linux x86_64 宿主；Go 1.24 Alpine 容器中运行 Go 测试、vet 和 build 通过。Docker legacy builder 构建 AMD64 镜像；UID 10001 容器健康检查和命名卷重建数据保留已实测。Linux/ARM64 Go 二进制交叉构建成功。
- Secure 项目 ACL 是本次第五阶段后续补齐项：ACL 凭据摘要、角色、项目范围及共享读写授权通过 REST/MCP/Web 共用 HTTP middleware 执行；列表响应过滤未授权资源，备份仅 Admin；相关跨身份测试详见 `cmd/server/authz_test.go`。
- MCP 服务端不依赖客户端 JSON Schema：逐工具校验必填参数、类型、枚举及未知字段。Private/Secure 回归确认缺失或非法 `memory_delete.action` 在即使提供有效写签名时也不会生成删除或审批请求；其他必填/类型组合由参数验证测试覆盖。
- Secure 本地端到端使用 TLS 和按 token hash 配置的项目 ACL。真实 headless Chromium/Playwright 下载审批 envelope，再将该浏览器文件交给 CLI TTY 并写入 TLS 服务，读回确认成功（confirm 与 `approve` 为自动输入）。Pi 1.6.0/openai-codex 与 Codex CLI 0.171.0 交互式 TUI 都实际搜索命中该记忆；在 Codex 一次性允许 MCP tool 后，明确用户请求的 `memory_save` 返回 `approval_required=true`，SQLite 确认未落库。Codex 非交互 `exec` 因默认 approval policy `never` 拒绝 MCP tool call，交互 TUI 配置 `on-request` 可用。临时 TLS 代理只记录方法、MCP 版本、工具名/参数名及状态，不记录 bearer/signature 值。
- 以 UID 65534（nobody）执行只读项目 API 成功、直接写返回 403；在目录可遍历时也无法读取 owner `0600` 审批私钥。该账号没有 Codex/Pi 安装及模型登录配置；`/home/ubuntu` 为 0750，未降低权限或复制 OAuth 凭据。真实 Codex/Pi 和审批 CLI 都以 UID 1000 运行；Ubuntu 账户有 sudo/docker 组权限，因此此处不构成 Agent/审批者隔离验证。
- WAL 回归使用子进程 `os.Exit` 制造有效未 checkpoint WAL/SHM；验证失败时原始数据库文件与 sidecar byte-for-byte 保留，成功替换后 sidecar 不残留，旧 WAL 事务不混入。Schema 测试覆盖仅伪造 version 的无关 SQLite 数据库。
- 当前环境无 Docker Compose/buildx 插件和 ARM64 设备；Tailscale 已连接，但仅确认本机在线，未做第二设备连通/项目绑定测试。首次 Codex 本地测试的自签 CA-as-server certificate 在 HTTP/MCP 请求前失败；换成由临时 CA 签发、SAN/serverAuth 完整的 TLS leaf 且把测试 CA 与系统 CA 合并提供给 Codex 后，初始化、工具列表及工具调用均返回成功。未验证生产代理拓扑/日志配置、OS 用户/终端/Docker daemon 隔离或生产恢复；阶段三跨设备和用户验收仍未完成。
